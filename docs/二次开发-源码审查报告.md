## 2. 架构现状（代码级验证）

```
前端 Vue3 SPA
   │ Axios
   ▼
JwtAuthenticationFilter（Bearer token → request attribute）
   ▼
Controllers（auth / user / group / document / qa / assistant / metrics）
   ▼
Services ──► MyBatis-Plus（业务表，PG）
   │                ├─ LambdaQueryWrapper（绝大多数据访问）
   │                └─ XML Mapper（14 个，含 FOR UPDATE 行锁）
   ├─► PgVectorRetrievalAdapter ──► Spring AI VectorStore（pgvector）★已抽象
   ├─► ElasticsearchChunkIndexService（自实现 HTTP 客户端）
   ├─► MinioStorageService / MissingObjectStorageService（条件装配）
   └─► DashScope（Chat qwen-plus / Embedding text-embedding-v3, 512 维）
```

**关键发现（对迁移有利）：**
1. **向量访问已被 `VectorStore` 接口隔离**（`engine/pgvector/PgVectorRetrievalAdapter`），且检索强制 `groupId` 过滤 + 结果二次校验——换向量后端不动业务代码。
2. **Java 层零原生 SQL、零 JdbcTemplate**，PG 依赖集中在 DDL 与少量 XML。
3. 前后端分离干净，前端仅通过 `/api` 通信，数据库迁移对前端无感。

## 3. PostgreSQL 专属依赖清单（MySQL 迁移改点）

### 3.1 DDL 层（sql/schema.sql，16 张表）

| PG 特性 | 出现位置 | MySQL 对策 |
|---|---|---|
| `BIGSERIAL` | 全部 16 张表主键 | `BIGINT NOT NULL AUTO_INCREMENT` |
| `JSONB` | `document_chunks.metadata_json`、`assistant_messages.structured_payload`、`vector_store.metadata` | `JSON` 类型 |
| `BOOLEAN` / `TRUE/FALSE` | 多表 | `TINYINT(1)`（`true/false` 字面量 SQL 兼容，无需改） |
| 部分索引 `WHERE status='READY' AND deleted=FALSE` | `idx_documents_group_hash` | MySQL 不支持 → 改普通联合索引 `(group_id, file_hash, status, deleted)` |
| `COMMENT ON TABLE/COLUMN` | 全表 | 改为建表语句内联 `COMMENT '...'`（可脚本生成） |
| `CREATE INDEX IF NOT EXISTS` | 全部索引 | MySQL 不支持 → 迁移脚本需幂等设计（`schema_migrations` 版本表） |
| `CREATE EXTENSION vector` + `VECTOR(512)` + HNSW | `vector_store` 表 | **保留在 PostgreSQL**（路线 B） |
| **保留字冲突 `groups`** | 表名，3 个 XML + 实体引用 | MySQL 8.0 中 `GROUPS` 为保留字 → **建议改名 `argus_groups`**（比全量加反引号更稳） |
| `TIMESTAMP` 类型 | 多表 | 建议 `DATETIME(3)`（避开 TIMESTAMP 2038 限制与时区隐式转换） |
| `DECIMAL(12,6)`、`DOUBLE PRECISION` | 计费/得分字段 | `DECIMAL(12,6)`、`DOUBLE`，兼容 |

### 3.2 Mapper XML 层（14 个文件，实际只有 2 个文件需要改）

| 文件 | PG 专属语法 | 处数 | MySQL 改法 |
|---|---|---|---|
| `ingestion/DocumentChunkMapper.xml` | `metadata_json::text` | 2 | 直接 `metadata_json`（MySQL JSON 驱动返回字符串） |
| `metrics/LlmUsageRecordMapper.xml` | `EXTRACT(EPOCH FROM (MAX(created_at)-MIN(created_at)))` | 5 | `TIMESTAMPDIFF(SECOND, MIN(created_at), MAX(created_at))` |
| `metrics/LlmUsageRecordMapper.xml` | `TO_CHAR(created_at,'YYYY-MM-DD')` | 2 | `DATE_FORMAT(created_at,'%Y-%m-%d')` |

**以下语法 MySQL 8.0 直接兼容，无需修改：** `now()`、`LIMIT n OFFSET m`、`FOR UPDATE`、`= true/false`、`COALESCE/CASE WHEN/ROUND`、`ON DELETE CASCADE`。

### 3.3 Java 层

- 无原生 SQL、无 `JdbcTemplate`、无 PG 专属类引用 → **零改动**（除连接配置）。
- `pom.xml`：`postgresql` 驱动保留（pgvector 用），**新增 `com.mysql:mysql-connector-j`**。

### 3.4 配置层

- `application-dev.yml` 单数据源 → 路线 B 需要**双数据源**：主库 MySQL（MyBatis-Plus）+ 向量库 PG（Spring AI pgvector starter 指定独立 DataSource）。这是迁移的主要新增工作量。

## 4. 向量存储路线决策（阶段 2 前置决策）

| 维度 | 路线 A：MySQL + ES 向量 | **路线 B：MySQL + PG/pgvector（推荐）** |
|---|---|---|
| 改动面 | 换 `spring-ai-starter-vector-store-elasticsearch`，重写嵌入写入/检索配置，迁移向量数据，kNN + groupId 过滤行为需回归 | 业务表迁 MySQL，`vector_store` 留 PG，**业务代码零改动** |
| 运维成本 | 组件少一个（去 PG） | 维护两种关系库 |
| 检索质量风险 | ES kNN 与 pgvector HNSW 召回差异需全量回归评测 | 无变化 |
| 现有代码利用 | VectorStore 抽象可复用，但 ES 版 starter 的 filter 语义需验证 | 完全复用 |
| 适合场景 | 明确要"去 PG 化"简化部署 | 快速交付、风险最低 |

**建议：路线 B 起步**（与方案 2.1 判断一致）。待阶段 4 评测集建立后，若需去 PG 再评估路线 A，届时有指标可对比。

## 5. 原项目已实现能力 vs 方案差距对照

> 方案原则："先评估质量与边界，再决定是复用、补强还是替换"。以下为逐项核对结果，**避免重复开发**。

### 5.1 阶段 3（ETL 可靠性）——原项目已实现约 70%

| 方案要求 | 原项目现状 | 结论 |
|---|---|---|
| 文件指纹去重 | `documents(group_id, file_hash)` 部分索引 + 上传秒传/续传（`document_upload_sessions` 三阶段） | ✅ 已实现 |
| 任务状态机 | `ingestion_jobs`：PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED + `retry_count/max_retries/next_retry_at/worker_id/last_error` | ✅ 已实现（字段比方案草案更全） |
| 幂等领取 | `claimRunning` CAS 式 UPDATE（status+worker_id 条件），`markSucceeded/markFailed` 带乐观校验 | ✅ 已实现 |
| 重试退避 | `@Retryable` + `@Recover`（Spring Retry）+ `next_retry_at` 调度 | ✅ 已实现 |
| 上传校验 | 大小/扩展名/分片哈希（`document_upload_chunks.chunk_hash`） | ⚠️ MIME 内容校验待确认 |
| 服务重启恢复 | 未发现启动时回收遗留 RUNNING 任务的逻辑 | ❌ **缺口 1：僵尸任务回收** |
| 删除后索引清理 | jobs 查询排除已删文档，但向量/ES 索引清理链路待验证 | ❌ **缺口 2：待验证** |

### 5.2 阶段 4（RAG 质量）——数据基础已具备

- `qa_records` + `qa_record_citations` 已记录 vector_score/keyword_score/hybrid_score/evidence_level —— **评测集可直接从历史记录构建**。
- 已有：查询规划（DIRECT/REWRITE/DECOMPOSE）、RRF 融合、四级证据评估、拒答。缺的是**离线评测流程与指标计算**。

### 5.3 阶段 5（权限安全）——基础扎实

- 向量检索强制 `groupId` 过滤 + 结果二次校验（防泄露）；ES 检索同样带 `groupId`；群组三级角色。
- 缺：越权测试用例、提示词注入防护、部分审计。

### 5.4 阶段 6-7（性能/部署）

- `deploy/` 已有双机 compose（server-a/b）+ 国内镜像源指南 + `.env.example`。
- 已有 Actuator；缺：结构化指标、请求/任务关联 ID、性能基线。

## 6. 阶段 2 迁移实施清单（MySQL，按依赖顺序）

1. `pom.xml` 新增 `mysql-connector-j`
2. 新建 `sql/schema-mysql.sql`（16 张业务表 DDL 转换 + `argus_groups` 改名 + 幂等迁移版本表）

4. 配置双数据源：主 MySQL（MyBatis-Plus 自动配置）+ PG（`PgVectorStore` 指定专用 DataSource Bean）
5. 改 2 个 Mapper XML（§3.2 共 9 处）
6. `groups` → `argus_groups`：改 1 个 `@TableName` + 3 个 XML 中的表名（连带 FK 引用）
7. 实体 `@TableId(type = IdType.AUTO)` 验证（MySQL 自增兼容，预计零改动）
8. 迁移数据校验脚本（行数 + 关键字段抽样）
9. 回归：编译 → 单测 → 端到端流程（上传→处理→问答→删除）

## 8. 审查结论

1. 原项目质量高于方案预期，**阶段 3 大部分、阶段 5 大部分已实现**，二次开发重点应为：MySQL 迁移（阶段 2）、缺口补齐（僵尸任务回收、删除索引清理验证）、评测体系（阶段 4）、测试与部署固化（阶段 7）。
2. MySQL 迁移真实改动面：**1 个 pom + 2 个 XML + 1 个表名 + 双数据源配置 + 2 份 DDL 脚本**，风险集中在双数据源装配与 `groups` 改名的完整性。
3. 建议采用路线 B（MySQL + pgvector 双库），后续以评测指标驱动是否进一步收敛到单库。

**实施中的新发现（审查阶段未覆盖）：**
1. `RETURNING id`（小写）在初次大小写敏感扫描中漏检，教训：**方言扫描必须 `-i` 不区分大小写**。
2. 存量测试 Bug：`HybridChunkRetrievalServiceTest` 未随 `YoucomSearchService` 构造参数演进更新，已修复（补 mock + 传参）。
3. 实体 status 字段为枚举类型（EnumTypeHandler 存 name()），MyBatis-Plus insert 需传枚举而非字符串。

**待环境验证（需用户提供 MySQL/PG 连接）：** 启动应用 → 注册/登录 → 建群 → 上传文档 → ETL → 问答 → 删除，全链路回归（见 `sql/README-migration.md` 第 3 节）。
