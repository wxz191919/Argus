# 阶段 6：性能与可观测性报告

> 测试时间：2026-10-11 ｜ 环境：本机单机（后端/MySQL/PG/ES/MinIO 同机，JDK 21）
> 交付：Actuator 指标暴露、慢 SQL 拦截器、可重复压测脚本与基线数据

## 1. 可观测性建设

### 1.1 指标暴露（commit 本次新增）

- `management.endpoints.web.exposure.include: health,info,metrics,threaddump`
- 当前暴露 **61 个指标**，覆盖：HikariCP 连接池（active/idle/timeout）、
  Tomcat 线程与请求、JVM 内存/GC、executor 队列积压（可监控 ETL 异步任务积压）、磁盘
- 所有指标打 `application=argus-rag` 标签，可直接被 Prometheus 抓取

### 1.2 慢 SQL 拦截器（新增 `SlowSqlInterceptor`）

- 拦截 MyBatis Executor 层 query/update，统计真实执行耗时
- 超过阈值（`argus.observability.slow-sql-threshold-ms`，默认 1000ms）输出 WARN：
  耗时 + Mapper ID + SQL + 参数摘要（截断防刷屏）
- 与已有 `LogAop`（接口级入参/耗时/返回值日志）形成"接口 + SQL"两级定位

### 1.3 请求关联

- `@OperationLog` + LogAop 已覆盖全部 Controller，记录方法/入参/耗时/结果
- 日志含任务 ID、文档 ID 等业务关联字段（ETL/回收日志均有 documentId）

## 2. 压测基线（可重复：`performance/load_test.py`）

### 2.1 结果

| 场景 | C=10 RPS | C=10 P95 | C=30 RPS | C=30 P95 | 错误 |
|---|---|---|---|---|---|
| S1 登录（BCrypt+DB） | 5.0 | 2091ms | 5.0 | 6560ms | 0 |
| S2 群组列表（联表） | 195.6 | 96ms | 318.5 | 138ms | 0 |
| S3 文档列表（权限过滤联表） | 212.4 | 103ms | 312.9 | 150ms | 0 |
| S4 健康检查（无 DB） | 393.1 | 40ms | 466.9 | 101ms | 0 |

原始数据：`docs/load-test-result.json`（覆盖 C=10/C=30 两档）。

### 2.2 分析

1. **业务查询 P95 < 150ms**（C=30 并发），离方案 P1 目标充足；吞吐随并发近似线性，未出现资源瓶颈；
2. **登录接口是已知设计瓶颈**：BCrypt 密码哈希是 CPU 密集的**故意慢操作**（防暴力破解），
   C=30 时 P95 达 6.5s——这是安全特性而非缺陷，但建议：
   - 登录接口加限流（同 IP 5 次/分钟），防止慢哈希被滥用为 DoS 放大点；
3. **单测/压测均未出现慢 SQL**（阈值 1s，压测期间日志零 WARN），17 张表的索引设计（迁移时内联）有效。

### 2.3 问答链路延迟（阶段 4 评测数据，串行）

- RAG 问答（检索 + LLM 生成）：P50 1.89s / P95 3.72s
- 构成：ES/PG 检索 < 100ms，其余为 DashScope embedding + qwen-plus 生成耗时（外部依赖）

## 3. 复现方式

```bash
python performance/load_test.py [并发数] [请求数]   # 默认 10 / 200
curl http://127.0.0.1:10001/actuator/metrics        # 查看指标列表
```

## 4. 后续建议

1. 登录限流（配合 Spring Cloud Gateway 或简单 Bucket4j）；
2. Prometheus + Grafana 抓取 /actuator/prometheus（需加 micrometer-registry-prometheus 依赖）；
3. ETL 队列积压告警（executor.queued 指标 > 阈值时通知）；
4. MySQL 慢查询日志（slow_query_log）与拦截器双保险。
